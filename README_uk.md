# NovaPay Payment для Magento 2 (українською)

`novapay/module-payment` (`NovaPay_Payment`) інтегрує еквайринг [NovaPay](https://novapay.ua) у
чекаут Magento 2. Покупець оплачує карткою, Apple Pay, Google Pay або застосунком NovaPay на
захищеній платіжній сторінці NovaPay - дані картки ніколи не потрапляють у ваш магазин (SAQ-A).
Статус замовлення змінюється лише за підписаними серверними **постбеками** від NovaPay - ніколи за
самим лише редіректом у браузері покупця.

Дві моделі оплати (обираються в налаштуваннях):

- **Direct (пряма)** - кошти списуються одразу під час оплати.
- **Hold (холд)** - кошти блокуються на картці, підтвердження списання ви робите пізніше (протягом
  29 днів), можливо частково; NovaPay автоматично повертає непідтверджений залишок.

Full English version: [`README.md`](README.md).

## Вимоги

- Magento 2.4.8, патч-рівень p1–p5 (Open Source або Adobe Commerce).
- PHP 8.3 або 8.4.
- Розширення PHP `openssl` та `json` (стандартні для Magento 2.4.8).
- Публічно доступний фронтенд магазину - NovaPay повинен мати можливість надсилати POST-запити на
  URL постбеку (див. [Налаштування URL постбеку](#налаштування-url-постбеку)).

## Встановлення

### Варіант A - zip-архів / копіювання в `app/code` (рекомендовано наразі)

Пакет `novapay/module-payment` **ще не опубліковано в Packagist** - це єдиний спосіб встановлення,
що працює сьогодні. Composer-варіант (Варіант B нижче) стане доступним пізніше.

1. Розпакуйте вміст модуля так, щоб `registration.php`, `composer.json`, `etc/`, `Gateway/`,
   `Model/` тощо опинилися безпосередньо в:

   ```
   <корінь-magento>/app/code/NovaPay/Payment/
   ```

2. Виконайте з кореня Magento:

   ```bash
   bin/magento module:enable NovaPay_Payment
   bin/magento setup:upgrade
   bin/magento setup:di:compile
   bin/magento cache:flush
   ```

3. **Лише для production mode** - також виконайте деплой статичного контенту перед тим, як
   обслуговувати реальний трафік (`setup:di:compile` сам по собі цього не робить):

   ```bash
   bin/magento setup:static-content:deploy -f
   ```

### Варіант B - Composer

`composer require novapay/module-payment` спрацює після публікації пакета на Packagist. **Доки
цього не сталося**, ця команда не має що встановлювати - потрібно вказати Composer, де знайти пакет,
за допомогою [VCS- або artifact-репозиторію](https://getcomposer.org/doc/05-repositories.md), що
посилається на вашу копію цього коду. Додайте це до кореневого `composer.json` вашого Magento-проєкту
(замініть `<repository-url>` на реальну URL-адресу - Git-репозиторій, або шлях/zip, який ви хостите
самостійно; наведений нижче приклад із заповнювачем не спрацює як є):

```jsonc
{
    "repositories": [
        {
            "type": "vcs",
            "url": "<repository-url>"
        }
    ]
}
```

Далі, з кореня Magento:

```bash
composer require novapay/module-payment
bin/magento setup:upgrade
bin/magento setup:di:compile
bin/magento cache:flush
```

(і, у production mode, `bin/magento setup:static-content:deploy -f`, як у кроці 3 Варіанту A).

Після `setup:upgrade` буде створено шість власних статусів замовлень (`novapay_pending`,
`novapay_holded`, `novapay_paid`, `novapay_expired`, `novapay_failed`, `novapay_refunded`), а метод
оплати "NovaPay" з'явиться (**вимкнений за замовчуванням**) у
**Stores → Configuration → Sales → Payment Methods → NovaPay**.

## Огляд налаштувань

Усі поля - у **Stores → Configuration → Sales → Payment Methods → NovaPay**. Кожне поле можна
задати на рівні сайту/магазину, як і будь-який стандартний метод оплати Magento, **зокрема й**
поля **Public Key** та **Postback Version**, які використовуються для перевірки й розбору вхідних
постбеків: вони читаються для магазину, який Magento визначає за *URL самого запиту постбеку*. Тому
сайт (website) із власним доменом може працювати з власним акаунтом NovaPay. Це **не** охоплює лише
випадок, коли кілька store view мають спільний домен без коду магазину в URL - тоді до всіх
постбеків цього домену застосовується store view за замовчуванням (а отже, конфігурація рівня
сайту). Повне правило - у [Поширених запитаннях](#поширені-запитання).

| Поле | Призначення |
| --- | --- |

| **Public Key** | Публічний ключ **NovaPay** (не ваш), перевіряє підписи вхідних постбеків. Читається на рівні магазину, визначеного за URL запиту постбеку (примітка 2). |

Показує повну адресу постбеку для обраного рівня налаштувань: store view - його власний захищений базовий URL, website - його store view за замовчуванням, рівень Default - store view за замовчуванням основного website. Скопіюйте її в кабінет мерчанта NovaPay. Це той самий рядок, який модуль автоматично передає як `callback_url`. Див. [Налаштування URL постбеку](#налаштування-url-постбеку). |
| **Payment Type** | `Direct` (списання одразу) або `Hold` (блокування коштів із подальшим підтвердженням). |
| **Кнопка «Повернення» NovaPay у деталях замовлення** | За замовчуванням **Ні**. Якщо **Так**, замовлення, оплачені через NovaPay, отримують у деталях замовлення одну кнопку **Повернення** замість **Credit Memo** (деталі замовлення та рахунку-фактури), **Void** (деталі замовлення) і **Refund Offline** (форма credit memo). Для холду кнопка знімає холд (стандартне скасування замовлення), для оплаченого замовлення відкриває форму повернення і створює стандартний онлайн credit memo. Замовлення з іншими методами оплати не змінюються. Див. [Кнопка «Повернення» NovaPay (опція)](#кнопка-повернення-novapay-опція). |
| **Кнопка «Підтвердити холдування» NovaPay у деталях замовлення** | За замовчуванням **Ні**. Якщо **Так**, замовлення NovaPay у статусі «на утриманні» отримує в деталях замовлення кнопку **Підтвердити холдування**, а стандартна кнопка **Invoice** для замовлень NovaPay приховується. Кнопка відкриває форму із сумою холдування і сумою підтвердження (менша сума означає часткове підтвердження, для нього потрібен **ідентифікатор отримувача**); підтвердження створює стандартний онлайн рахунок-фактуру. Замовлення з іншими методами оплати не змінюються. Див. [Кнопка «Підтвердити холдування» NovaPay (опція)](#кнопка-підтвердити-холдування-novapay-опція). |
| **Postback Version** | Реалізовано лише `v3`, це значення за замовчуванням (примітка 3). |
| **Success URL** / **Fail URL** | Необов'язкові перевизначення сторінок успіху та невдачі Magento (примітка 4). |
| **Success Redirect Timeout (sec)** | За замовчуванням 5. Через скільки секунд сторінка результату NovaPay автоматично перенаправляє покупця на Success URL. 0 вимикає автоматичне перенаправлення, і покупець натискає кнопку на сторінці NovaPay. Передається в NovaPay як `success_redirect_timeout` лише якщо значення більше 0. |
| **Recipient Identifier (ЄДРПОУ/ІПН)** | Обов'язковий лише для часткового захоплення холду. |
| **Enable Logging** | Так/Ні, за замовчуванням Ні. Логує кожен запит, відповідь і постбек у `var/log/novapay.log`. Критичні помилки логуються завжди, незалежно від цього перемикача. |
| **Convert Phone to +380 Format** | Увімкнено за замовчуванням. Перетворює телефон з адреси оплати, введений як `0XXXXXXXXX` або `380XXXXXXXXX`, у формат `+380XXXXXXXXX` перед надсиланням до NovaPay. |
| **Validate Phone Number (+380 mask)** | Увімкнено за замовчуванням. Відхиляє оформлення замовлення, якщо телефон не відповідає українській масці +380 (примітка 5). |
| **Phone Validation Error Message** | Текст, який бачить покупець при відхиленні номера. |
| **Sort Order** | Позиція методу в списку методів оплати. |

Примітки:

1. Відсутність телефону в адресі оплати метод **не приховує**; що відбувається в цьому випадку,
   описано в [Усуненні проблем](#усунення-проблем-короткий-підсумок).
2. Підпис постбеку передається в **заголовку, що залежить від версії**: `x-sign-v2` для v3,
   `x-sign` для застарілих v1/v2. Модуль обирає потрібний заголовок за налаштуванням
   **Postback Version** (v3 підтверджено на живому постбеку NovaPay).
3. Читається на рівні магазину, визначеного за URL запиту постбеку (як і **Public Key**).
   Список пропонує `v1` та `v2` для майбутньої сумісності, але якщо обрати їх (або якщо у вашому
   кабінеті NovaPay налаштовано v1/v2), модуль відкидає **кожен** вхідний постбек без обробки й
   пише попередження з `reason: "unimplemented_version"`; HTTP 200 усе одно повертається NovaPay.
   Встановіть версію постбеку у кабінеті NovaPay на **v3** і залиште це поле за замовчуванням.
4. **Невирішене питання:** ці роути приймають лише GET, див.
   [Усунення проблем](#усунення-проблем-короткий-підсумок).
5. Перевіряються телефон в адресі доставки (для віртуальних замовлень крок доставки відсутній, тож
   перевірка пропускається) та телефон в адресі оплати. Некоректний телефон доставки повертає
   покупця на крок доставки, некоректний телефон оплати лишає його на кроці оплати, бо саме там у
   Luma розташована форма оплати. До NovaPay завжди надсилається лише телефон з адреси оплати:
   телефон доставки лише перевіряється, але ніколи не передається. Два телефонні перемикачі
   незалежні: вимкнення конвертації скасовує лише перетворення, а перевірка за маскою (якщо
   увімкнена) усе одно застосовується до введеного значення.

### Група відображення статусів (Order Status Mapping)

Для кожного статусу сесії NovaPay є свій випадаючий список:

| Статус сесії NovaPay | Стан замовлення Magento (фіксований) | Статус за замовчуванням |
| --- | --- | --- |
| `created` | `new` | Pending NovaPay Payment (`novapay_pending`) |
| `processing` | `pending_payment` | Pending Payment (`pending_payment`) |
| `holded` | `processing` | NovaPay Hold Authorized (`novapay_holded`) |
| `hold_confirmed` | `processing` | Paid via NovaPay (`novapay_paid`) |
| `paid` | `processing` | Paid via NovaPay (`novapay_paid`) |
| `failed` | `pending_payment` | NovaPay Payment Failed (`novapay_failed`) |
| `voided` | `closed` | Refunded via NovaPay (`novapay_refunded`) |
| `voided` після часткового повернення | без змін (`processing`) | замовлення лишається Paid via NovaPay (`novapay_paid`) |
| `expired` | `canceled` | NovaPay Session Expired (`novapay_expired`) |

Для `failed` і `voided` використовуються власні статуси модуля замість стандартних Pending Payment /
Closed, тож невдалу оплату NovaPay або повернення через NovaPay можна відрізнити від інших замовлень,
що очікують оплати, чи ручного закриття.

Невдала оплата **не** скасовує замовлення. NovaPay дозволяє покупцю повторити оплату на платіжній
сторінці в межах тієї самої сесії, тому після `failed` замовлення лишається в стані `pending_payment`
(товар лишається зарезервованим), а наступні `processing`, `holded`, `paid` чи `hold_confirmed` для
цієї сесії застосовуються як звичайно; `expired` скасовує замовлення. Запізнілий `failed` від
попередньої спроби, що надійшов після `holded`, ігнорується (WARNING `stale_failed_after_hold`), тож
замовлення з холдом не повертається в очікування оплати.

Стандартний cron Magento скасовує лише замовлення зі *статусом* `pending_payment`, тому замовлення
NovaPay Payment Failed він пропускає. Це робить get-status cron модуля (кожні 15 хвилин): якщо NovaPay
і далі повертає `failed`, а замовлення старше за **Pending Payment Order Lifetime**
(`sales/orders/delete_pending_after`, за замовчуванням 480 хвилин від створення замовлення),
замовлення скасовується, товар повертається на склад, статус лишається NovaPay Payment Failed (тепер
у стані `canceled`), додається коментар в історії для адміністратора (`cron.failed_order_expired` у
лозі).

Скасоване чи закрите замовлення Magento постбек ніколи не відкриває знову, незалежно від збереженого
статусу NovaPay: до нього застосовуються лише `expired` і `voided`. Наступні `holded`, `paid` чи
`hold_confirmed` не застосовуються: замовлення лишається скасованим, а в лог пишеться CRITICAL
`money_taking_resurrection` для ручної звірки; інші статуси логуються як WARNING `order_closed`. Замовлення, скасовані постбеком `failed` до цієї зміни, лишаються скасованими; для них
`novapay_failed` і далі призначений стану `canceled`, а data patch
`AssignFailedStatusToPendingPaymentState` додатково призначає його стану `pending_payment`. Якщо в
рядку Failed збережено статус стану `canceled` (наприклад стандартний Canceled), модуль використає
`novapay_failed` і запише попередження `config.status_label_invalid`; виберіть там статус стану
Pending Payment.

Під час оновлення data patch
`MigrateFailedAndVoidedStatusDefaults` замінює на нові статуси збережені на рівні Default Config
значення Canceled для Failed і Closed для Voided (старі стандартні значення). Будь-яке інше
збережене значення, а також перевизначення на рівні сайту чи вітрини, не змінюється.

Кожен випадаючий список показує лише статуси, призначені фіксованому стану цього рядка (власний
статус можна призначити стану в **Stores → Settings → Order Status**).

Важливо: **налаштуванню підлягає лише назва (лейбл) статусу, а не саме "стан" замовлення**,
тобто ви можете перейменувати відображувану назву, але не можете прив'язати `paid` до стану
`complete` чи `canceled`. Це протокольне обмеження модуля, не налаштування мерчанта: якщо
збережена назва не належить потрібному стану, модуль пише попередження в лог і використовує
стандартну назву за замовчуванням, некоректний стан ніколи не застосовується.

Два транзитні статуси сесії (`processing_hold_completion`, `processing_void`) у списку відсутні -
вони ніколи не змінюють статус замовлення (постбек із таким статусом лише логується). Частковий
постбек про повернення коштів також не змінює статус замовлення - лише фіксує суму повернення по
позиції; статус переходить у `voided` тільки після повного повернення всієї сесії.

Кожна застосована подія NovaPay записується в історію замовлення. Кожен постбек, що змінює
замовлення, і кожна синхронізація get-status через cron додають один коментар лише для
адміністратора (покупець його не бачить і не отримує сповіщення), наприклад "NovaPay: отримано
статус paid (postback). Сума 39.00 UAH, RRN 9770660, тип оплати card, час NovaPay
2026-08-03T06:19:11.954+00:00." Джерело - `postback` або `get-status`, відсутнє в події значення
показується як `-`. Час NovaPay - це значення `created_at`, яке надсилає NovaPay. Дублікати,
транзитні статуси та заблоковані переходи коментарів не додають.

Кнопки **Invoice**, **Ship** і **Hold** приховані на замовленнях NovaPay, що ще очікують оплату.
Доки NovaPay не повідомить, що кошти заблоковано або списано (`holded`, `hold_confirmed` чи `paid`),
перегляд замовлення не пропонує цих трьох кнопок, тож ніхто не зможе провести офлайн-рахунок за
гроші, яких не надходило. Кнопка **Cancel** лишається. Замовлення з іншими методами оплати це не
зачіпає.

Статус Pending NovaPay Payment (`novapay_pending`) призначений лише стану `new`. Попередні версії
призначали його також стану `pending_payment`, тому в **Stores > Settings > Order Status** він
показувався двічі. Data patch `UnassignPendingStatusFromPendingPaymentState` під час оновлення
прибирає друге призначення. Якщо для рядка Processing було збережено Pending NovaPay Payment, це
значення більше не дійсне для цього рядка: модуль використовує Pending Payment і пише в лог
попередження `config.status_label_invalid`. Оберіть для цього рядка Pending Payment, щоб прибрати
попередження.

### Генерація ключів

Створіть пару RSA-ключів мерчанта (і зареєструйте публічний ключ у NovaPay) за офіційною
інструкцією NovaPay:
<https://nova-pay.atlassian.net/wiki/spaces/EXT/pages/694779954>

У поле Private Key вставте **свій приватний** ключ, а у Public Key - **публічний ключ NovaPay**
(не свій!) - це дві різні пари ключів.

### Налаштування URL постбеку

Ендпоінт постбеку модуля має фіксовану адресу на захищеному базовому URL store view, наприклад
`https://shop.example.com/novapay/postback/index/`. Складати її вручну не потрібно: поле
**Postback URL** (лише для читання, одразу під **Public Key**) у розділі налаштувань NovaPay показує
повну адресу для обраного рівня налаштувань. Перемкніть вибір scope на потрібний store view, щоб
побачити його адресу; рівень Default показує store view за замовчуванням основного website, рівень
website - його store view за замовчуванням.

Скопіюйте значення з цього поля й зареєструйте його в кабінеті мерчанта NovaPay (Acquiring3). Воно
збігається з `callback_url`, який модуль автоматично передає при кожному викликові `/v1/session`, тож
вручну вводити адресу в налаштуваннях модуля не потрібно. Поле лише показує значення, нічого не
зберігається.

**Цей модуль реалізує лише версію постбеку v3.** У кабінеті мерчанта NovaPay встановіть версію
постбеку на **v3** - не залишайте v1 чи v2. Якщо версія постбеку (з будь-якої сторони) не v3, модуль
відкидає кожен вхідний постбек без обробки - див. рядок **Postback Version** вище та [Усунення
проблем](#усунення-проблем-короткий-підсумок).

Адреса має бути доступна з інтернету напряму (без VPN чи basic-auth) - NovaPay звертається до неї
сервер-сервер, а не через браузер покупця.

## Тестовий режим

1. Test Mode = Yes.
2. Merchant ID = `2` (опублікований спільний тестовий мерчант NovaPay).
3. Private Key / Public Key - тестова пара ключів з
   <https://novapay.readme.io/reference/authentication>.
4. Оформіть замовлення з оплатою NovaPay і оплатіть тестовою карткою:
   <https://novapay.readme.io/reference/testing-data>.
5. Перевірте `var/log/novapay.log` - там мають з'явитися виклики `/v1/session`,
   `/v1/payment` та вхідний постбек.

**Не використовуйте тестові ключі та merchant_id `2` при Test Mode = No** - виробничий конфіг з
такими значеннями свідомо блокується релізним чек-листом модуля.

## Режим Hold (холд)

При **Payment Type = Hold**: замовлення переходить у статус "NovaPay Hold Authorized" після
постбеку `holded` (кошти заблоковано, ще не списано). З перегляду замовлення створіть **Invoice** з
типом захоплення **Capture Online**:

- Повна сума → NovaPay списує весь холд.
- Зменшена сума (часткове захоплення) → потрібно заповнити **Recipient Identifier (ЄДРПОУ/ІПН)**;
  залишок NovaPay автоматично повертає покупцю. Після підтвердження захоплення модуль стандартним
  способом Magento скасовує кількість без рахунка (у товарах вона позначена як Canceled, у
  підсумках показано Total Canceled, залишки повертаються на склад), тому кнопка **Invoice**
  зникає і ніхто не зафіксує оплату звільненої суми. До замовлення додається один коментар
  зі списаною та звільненою сумами, зі статусом оплаченого замовлення, мовою адмінки за
  замовчуванням (Stores → Configuration → General → Locale Options на рівні Default Config). Подальше повне
  повернення списаної суми закриває замовлення.
- Захоплення можливе лише **протягом 29 днів** з моменту холду (модуль перевіряє це і на своєму
  боці).
- На сесію можливий лише **один** виклик complete-hold - повторного "донабору" суми не існує.

**Після створення інвойсу замовлення перебуває у стандартному стані Magento `payment_review`, доки
не прийде постбек `hold_confirmed`.** Це очікувана поведінка NovaPay, а не збій чи "застигле"
замовлення - інвойс свідомо створюється як непідтверджений і стає оплаченим лише після серверного
підтвердження. Якщо постбек `hold_confirmed` не прийшов, його підхопить крон-завдання
`novapay_sync_status` (кожні 15 хв, через `/v1/get-status`).

Щоб скасувати непідтверджений холд замість захоплення - використайте **Cancel** або **Void** на
замовленні (`/v1/void`, скасовує весь холд). **Часткове скасування холду не підтримується.**

**Кнопки Hold / Unhold Magento - це не холд NovaPay.** Це стандартне службове утримання замовлення
(стан `holded`), яке нічого не надсилає в NovaPay і лише блокує інші дії на замовленні. Покроковий
посібник для адміністратора з таблицею «яка кнопка що робить»: `docs/admin-hold-operations.uk.md`.

## Повернення коштів (Refund)

Повернення коштів виконується через `/v1/void` NovaPay, мапиться на стандартний онлайн credit memo
Magento. Це **інша** нативна дія, ніж скасування холду (дія **Void**), описане вище в
[Режим Hold (холд)](#режим-hold-холд) - обидві звертаються до того самого ендпоінту NovaPay, але
credit memo існує лише після того, як замовлення вже було виставлено рахунком/оплачено; скасування
ще не захопленого холду не має рахунку для повернення й використовує дію **Void** замовлення, а не
credit memo.

Повне повернення (усі позиції) та часткове повернення по позиціях виконуються через credit memo.
Часткове повернення **не змінює статус замовлення** - сума фіксується по позиції, і кнопка
повернення залишається доступною, доки всю суму сесії не буде повернено (постбек `voided`), хоча
загалом на замовлення приймається лише **одне** онлайн-повернення NovaPay (див. обмеження нижче).
NovaPay надсилає `voided` і після часткового повернення; модуль тоді запитує `/v1/get-status`,
скільки повернено, лишає замовлення в статусі Paid via NovaPay і додає коментар в історію "NovaPay
підтвердив часткове повернення: повернено ... з ..., решта лишається списаною." Для часткового
повернення, зробленого в NovaPay без кредит-ноти, додається коментар із проханням звірити вручну.
Повернення доставки можливе лише в межах **повного** повернення; коригувальні суми (adjustments) на
credit memo не підтримуються і блокуються. На сторінці credit memo завжди показано попередження:
"Часткове повернення можливе лише якщо замовлення було оплачено на рахунок NovaPay."

**Обмеження: одне повернення NovaPay на замовлення.** Ця інтеграція фіксує лише один ідентифікатор
операції NovaPay на замовлення (числовий id з відповіді `/v1/payment`). Не документовано, чи
викликаний **після** попереднього часткового повернення на тій самій сесії простий
`POST /v1/void` (без `operations[]`, форма "повного повернення") (a) повертає лише залишок, (b)
повертає всю первісну суму ще раз - тобто вдруге повертає вже повернену частину, чи (c) відхиляється
взагалі. Доки NovaPay не підтвердить, який з варіантів (a)/(b)/(c) застосовується, модуль
дозволяє **лише одне** повернення (повне або часткове) на замовлення, замість того, щоб вгадувати.
Повторна спроба явно блокується з поясненням в адмінці; для повернення залишку зверніться до
підтримки NovaPay.

**Офлайн-повернення не звертаються до NovaPay.** Якщо в credit memo обрано "Refund Offline" -
Magento скоригує лише власний облік, а кошти на боці NovaPay не повертаються. Використовуйте
онлайн-повернення для замовлень, реально оплачених через NovaPay.

## Кнопка «Повернення» NovaPay (опція)

Специфікація NovaPay передбачає одну кнопку **«Повернення»** у деталях замовлення замість екранів
credit memo Magento. Модуль надає її як опцію: **Кнопка «Повернення» NovaPay у деталях замовлення**
(`payment/novapay/refund_flow`, рівень store view, за замовчуванням **Ні**). Якщо **Ні**, нічого не
змінюється і використовується стандартний процес, описаний вище.

Якщо **Так**, для замовлень, оплачених через NovaPay:

- У деталях замовлення з'являється кнопка **«Повернення»** згідно зі статусом NovaPay: для холду
  (`holded`) і для оплаченого замовлення (`paid`, `hold_confirmed`). Для статусів created,
  processing, failed, expired і voided кнопки немає. Після повного повернення або зняття холду
  кнопка залишається до постбеку `voided` і відкриває форму лише для перегляду з повідомленням
  «Повернення оформлено, очікується підтвердження NovaPay.» (або «Зняття холду оформлено,
  очікується підтвердження NovaPay.»), кнопка підтвердження неактивна.
- Кнопки **Credit Memo** (деталі замовлення та рахунку-фактури), **Void** (деталі замовлення) і
  **Refund Offline** (форма credit memo) приховані. **Скасувати** залишається: для холду вона
  робить те саме, що й кнопка.
- **Холд:** кнопка просить підтвердження і скасовує замовлення стандартним скасуванням Magento.
  NovaPay отримує `POST /v1/void` без `operations[]`, холд знімається повністю (часткове скасування
  холду не підтримується). Повідомлення: «Холд знято, кошти розблоковано. Статус оновиться після
  підтвердження NovaPay.»
- **Оплачене замовлення:** кнопка відкриває форму повернення, по рядку на кожну оплачену позицію:
  товар, артикул, оплачено за одиницю, оплачена і повернена кількість, **Повернути на склад**,
  **Кількість до повернення** і **Вартість до повернення**. Нижче: **Загальна сума до повернення**,
  банер «Часткове повернення можливе якщо Оплата замовлення була на рахунок в NovaPay» і кнопка
  **Повернути через NovaPay**. Якщо не вказати жодної кількості, виконується повне повернення (усі
  залишкові позиції та доставка), кнопка спершу питає «Повернути всю суму замовлення (...)?». Якщо
  вказати кількості, це часткове повернення (доставка тоді не повертається).
- Після підтвердження модуль створює credit memo так само, як стандартна форма credit memo (ядровий
  завантажувач credit memo, та сама логіка складу і сум), і повертає його онлайн, тому діють той
  самий запит `POST /v1/void` і ті самі правила повернення, що описані вище. Повертається сума
  credit memo, розрахована Magento.
- Будь-яка помилка, наприклад відмова NovaPay, показується на формі, і нічого не зберігається: ні
  credit memo, ні змін у замовленні. Форма зберігає введені кількості, тож повторне підтвердження
  надсилає те саме часткове повернення, а не повне.
- Якщо повернення неможливе, форма повідомляє про це заздалегідь: після попереднього повернення
  (одне повернення NovaPay на замовлення, див. обмеження вище) кнопка підтвердження неактивна; для
  частково списаного платежу поля кількості неактивні і доступне лише повне повернення.

Права доступу: для форми повернення потрібен той самий ресурс ACL, що й для стандартного credit memo
(`Magento_Sales::creditmemo`), для зняття холду той самий, що й для стандартного скасування
(`Magento_Sales::cancel`). Скріншоти і подробиці: `docs/admin-online-refund.uk.md`.

## Кнопка «Підтвердити холдування» NovaPay (опція)

Специфікація NovaPay передбачає окрему кнопку **Підтвердити холдування** з полем суми в деталях
замовлення. Модуль надає її як опцію: **Кнопка «Підтвердити холдування» NovaPay у деталях
замовлення** (`payment/novapay/hold_confirm_flow`, рівень store view, за замовчуванням **Ні**). Якщо
**Ні**, нічого не змінюється і холд підтверджується стандартним рахунком-фактурою (див.
[Режим Hold (холд)](#режим-hold-холд)).

Якщо **Так**, для замовлень, оплачених через NovaPay:

- Стандартна кнопка **Invoice** у деталях замовлення приховується.
- Кнопка **Підтвердити холдування** відображається, поки статус NovaPay `holded`, на замовлення ще
  можна виставити рахунок-фактуру і з моменту холдування минуло не більше 29 днів. В інших статусах
  і для старішого холду кнопки немає.
- Кнопка відкриває форму із **сумою холдування**, станом **ідентифікатора отримувача** і полем
  **Сума підтвердження**, попередньо заповненим повною сумою холдування (базова валюта, 2 знаки
  після коми). Сума має бути більшою за 0 і не перевищувати суму холдування (перевіряється в
  браузері і на сервері). Менша сума означає часткове підтвердження: різницю NovaPay автоматично
  повертає платнику. Для часткового підтвердження потрібен **ідентифікатор отримувача
  (ЄДРПОУ/ІПН)**; без нього форма показує попередження і приймає лише повну суму.
- **Підтвердити холдування** у формі створює стандартний онлайн рахунок-фактуру (так само, як
  **Invoice** з **Capture Online**), тож модуль надсилає `POST /v1/complete-hold`: без суми для
  повного холдування, з `operations[{id, amount, recipient_identifier}]` для часткового.
  Рахунок-фактура лишається в очікуванні, а замовлення в статусі **Payment Review** до postback від
  NovaPay.
  У цей час кнопка відкриває форму лише для перегляду з повідомленням «Підтвердження холдування
  оформлено, очікується підтвердження NovaPay.». Після postback `paid` / `hold_confirmed` кнопки
  немає.
- **Часткові суми і рахунки-фактури.** Magento виставляє рахунок на цілі кількості товарів, а після
  postback від NovaPay модуль очікує, що сума рахунку дорівнює списаній сумі (після цього
  розблокований залишок скасовується). Тому часткова сума має відповідати цілим товарам разом із
  доставкою (перший рахунок-фактура завжди містить усю доставку). Модуль бере рядки замовлення по
  черзі і включає стільки цілих одиниць, скільки вміщує сума. Якщо сума збігається, вона
  надсилається як є. Якщо ні, нічого не надсилається: форма повертається з найближчою меншою
  сумою, що збігається, наприклад «... тому суму 80.00 не можна підтвердити точно. Найближча менша
  сума, що покриває цілі товари разом із доставкою: 60.00 (1 x Tee) ...», і цю суму підтверджують
  другим натисканням. Сума, менша за доставку плюс найдешевший товар, відхиляється.
- Будь-яка помилка, наприклад відмова NovaPay, показується у формі, і нічого не зберігається:
  рахунок-фактуру не створено, замовлення не змінено. Форма зберігає введену суму.

Права доступу: для форми потрібен той самий ресурс ACL, що й для стандартної кнопки Invoice
(`Magento_Sales::invoice`). Обидві опційні кнопки (повернення і підтвердження холдування) можна
увімкнути одночасно. Скріншоти і подробиці: `docs/admin-hold-operations.uk.md`.

## Логування

Якщо **Enable Logging = Yes** (за замовчуванням вимкнено; увімкніть на час налаштування або діагностики), кожен запит/відповідь API та кожен вхідний постбек
логуються у формат JSON (один об'єкт на рядок) у файл:

```
var/log/novapay.log
```

Кожен постбек записується двічі: у момент надходження (`"event":"postback.received"` - разом із
самим тілом запиту, а також `body_sha256`, `body_bytes`, `signature_present`, `postback_version`)
і окремо за результатом обробки (`postback.accepted`, `postback.duplicate`,
`postback.invalid_signature`, `postback.malformed`, `postback.unknown_session`,
`postback.stale_session`, `postback.blocked_transition`, `postback.store_mismatch`,
`postback.store_key_mismatch_rejected`). Запис про надходження робиться **до** перевірки підпису,
тож тіло відхиленого постбека теж залишається в логу - саме це дозволяє розібратися в причині
відмови.

Номер картки завжди маскується (наприклад `123456******1234`) - у тілі записаного постбека також;
телефон клієнта маскується так само, а приватний ключ ніколи не потрапляє в лог.

Два важливі моменти:

- **Файл швидко росте і потребує ротації**, оскільки логується кожен запит/відповідь/постбек.
  `var/log/novapay.log` лежить безпосередньо в `var/log/`, тож конфігурація logrotate зі шаблоном
  `var/log/*.log` (зокрема стандартна у хостинг-провайдерів) вже його охоплює; якщо ваша
  конфігурація перелічує файли явно - додайте `var/log/novapay.log`. Розширення для перегляду логів
  в адмінці, які показують лише файли верхнього рівня `var/log`, також його бачать.
- **Критичні помилки NovaPay пишуться лише в цей окремий лог**, а не в `system.log`/`exception.log`
  Magento. Якщо ваш моніторинг стежить лише за стандартними логами Magento, він пропустить ці
  випадки - додайте окреме правило моніторингу саме для `var/log/novapay.log` (наприклад,
  сповіщення на будь-який рядок JSON з `"level_name":"CRITICAL"`).

## Усунення проблем (короткий підсумок)

- **Замовлення з невдалою оплатою або неоплачене скасовано, а пізніше в `var/log/novapay.log` з'явився
  CRITICAL `money_taking_resurrection`** - скасування замовлення в Magento (кнопка **Cancel** або
  автоматичне скасування після часу життя неоплаченого замовлення) не закриває сесію NovaPay: покупець
  може оплатити її, доки вона не закінчиться. Модуль не відкриває скасоване замовлення знову і пише
  цей рядок. Це сигнал для звірки: перевірте сесію в кабінеті мерчанта NovaPay. Холд (`holded`) можна
  зняти там; пряму оплату (`paid` / `hold_confirmed`) потрібно повернути вручну в кабінеті NovaPay
  або зв'язатися з покупцем, бо скасоване замовлення Magento не можна оплатити чи повернути онлайн.

- **Метод не показується в чекауті** - перевірте: увімкнено; базова валюта магазину/кошика - UAH
  (NovaPay підтримує лише UAH). **Це два єдині гейти видимості методу.** Відсутність телефону в
  адресі оплати метод **не приховує** - див. наступний пункт про те, що насправді відбувається в
  цьому випадку.
- **Замовлення оформлено, але покупця повернуто в кошик з помилкою, і залишилось "осиротіле"
  замовлення зі статусом "Pending NovaPay Payment"** - це саме те, що відбувається, коли в адресі
  оплати немає телефону, **але** за стандартними налаштуваннями Magento (**Stores → Configuration →
  Customers → Customer Configuration → Name and Address Options → Show Telephone**,
  `customer/address/telephone_show`, за замовчуванням `Required`) сама форма чекауту блокує
  перехід далі клієнтською валідацією ("Це поле є обов'язковим."), щойно поле телефону лишається
  порожнім - тож без зміни цього налаштування оформити замовлення без телефону через стандартний
  чекаут Luma **неможливо**, і цей сценарій там не відтворюється. Він стає можливим лише якщо це
  налаштування змінено на `Optional` або `Hide` у відповідному скоупі (нативна функція Magento, не
  пов'язана з NovaPay), або якщо замовлення оформлюється шляхом, який обходить валідацію самої форми
  чекауту (оформлення через REST/GraphQL, створення замовлення в адмінці, або збережена адреса
  покупця, що існувала до зміни налаштування `telephone_show`). У будь-якому з цих випадків: сам крок
  оформлення замовлення **не** перевіряє наявність телефону, тож замовлення **створюється** так само,
  як і будь-яке інше замовлення NovaPay (статус `novapay_pending`); лише наступний крок - побудова
  сесії NovaPay на контролері редіректу, який виконується одразу після оформлення - виявляє
  відсутність `client_phone` (обов'язковий для `/v1/session`) і кидає виняток до будь-якого звернення
  до API NovaPay. Покупець бачить повідомлення "A phone number on the billing address is required to
  pay with NovaPay." і повертається в кошик; саме замовлення залишається незмінним. Це замовлення
  ніколи не отримало session id NovaPay, тож крон `novapay_sync_status` не має що опитувати і не
  вирішить цю ситуацію - замовлення залишається "осиротілим" у статусі pending, доки ви не скасуєте
  його вручну, або доки це не зробить нативне очищення замовлень Magento (**Stores → Configuration →
  Sales → Order Cleanup → Pending Order Lifetime (minutes)**, якщо це налаштовано - це функція ядра
  Magento, не пов'язана з NovaPay). Попросіть покупця додати номер телефону і оформити замовлення
  повторно.
- **Редірект на NovaPay після оформлення замовлення не вдається** - зазвичай проблема в
  налаштуваннях ключів: перевірте відповідність Merchant ID, Private Key та Test Mode; дивіться
  `var/log/novapay.log` для точного коду помилки NovaPay (наприклад `InvalidSignError`,
  `SystemError`).
- **Постбеки не приходять / замовлення "застигають"** - перевірте: (1) URL постбеку зареєстровано в
  кабінеті NovaPay точно так, як його показує поле **Postback URL** для store view, що приймає
  замовлення, і ця адреса містить реальний публічний домен магазину (див.
  [Налаштування URL постбеку](#налаштування-url-постбеку)); (2) URL доступний з інтернету без
  VPN/basic-auth; (3) **реалізовано лише версію постбеку v3** - якщо в кабінеті NovaPay або в полі
  Postback Version модуля обрано v1/v2, **кожен** постбек відкидається без обробки (лог із
  `reason: "unimplemented_version"`, HTTP 200 усе одно повертається NovaPay). Встановіть обидві
  сторони на v3. Крон `novapay_sync_status` (кожні 15 хв) підхоплює пропущені постбеки через
  `/v1/get-status` **лише для замовлень, які вже мають session id NovaPay** - переконайтеся, що крон
  Magento дійсно виконується, якщо це не вирішує "застигле" замовлення. Кожен запуск пише один рядок
  `cron.sync_summary` у `var/log/novapay.log` (якщо логування увімкнене); рядок
  `cron.sync_skipped_locked` лише означає, що другий процес крона стартував, поки попередній запуск
  ще тривав, і нічого не робив - це очікувана поведінка.
- **Перевірка підпису постбеку постійно провалюється** - у полі Public Key має бути публічний
  ключ **NovaPay** (не ваш власний), і саме той, що відповідає Test Mode (тестовий і production
  ключі різні). Підпис також приходить у **заголовку, що залежить від версії** - постбеки v3
  підписані в `x-sign-v2`, застарілі v1/v2 - у `x-sign`; модуль читає той заголовок, що відповідає
  налаштуванню **Postback Version**, тож це поле має збігатися з версією постбеку у вашому акаунті
  NovaPay (для v3, за замовчуванням, модуль читає `x-sign-v2`).
- **Покупець отримує 404 після повернення з NovaPay (success або fail)** - `novapay/success/index`
  і `novapay/fail/index` реалізовані лише як GET-роути. Чи NovaPay повертає покупця через GET, чи
  через POST, **ще не підтверджено на живому середовищі** - якщо це POST, покупець отримає 404. Це
  невирішене питання (див. "Known limitations" у `CHANGELOG.md`), яке потрібно перевірити (з
  підтримкою NovaPay або через тестовий тунель) до запуску в production.

## Поширені запитання

**Чи можна використовувати різні облікові дані NovaPay для різних магазинів (store view)?** Так -
для окремих **сайтів (websites) із власним доменом**; із застереженням для store view, що ділять
спільний домен. (Раніше ці два поля читалися без ідентифікатора магазину, а Magento і так трактує
це як *поточний* магазин - тож для звичайного веб-постбеку поведінка була такою самою; змінилося
те, що тепер скоуп заданий явно, коректний для CLI/cron і покритий тестами.)

Усі поля налаштувань, включно з Merchant ID та ключами, підтримують стандартні рівні конфігурації
(scope) Magento, тож вихідні виклики `/v1/session`/`/v1/payment` конкретного магазину вже
використовують саме його Merchant ID/Private Key. Поля **Public Key** та **Postback Version** для
*вхідних* постбеків читаються для магазину, який Magento визначає за URL запиту постбеку - за
доменом запиту (і кодом `___store`, якщо він є), і ніколи за вмістом payload, якому не можна
довіряти до перевірки підпису. Таке визначення надійне, бо модуль будує `callback_url` кожної сесії
з **базового URL того магазину, у якому оформлено замовлення**, тож справжній постбек завжди
повертається в той самий магазин.

Що це означає на практиці:

- **Окремі сайти, кожен на власному домені** - підтримується повністю. Кожен сайт може мати власний
  акаунт NovaPay: задайте Merchant ID, Private Key, Public Key і Postback Version на рівні цього
  сайту.
- **Кілька store view на спільному домені** - за URL постбеку їх не розрізнити, тому Magento
  визначає **store view за замовчуванням** для цього сайту, і саме його конфігурація
  використовується для перевірки та розбору. Або тримайте Public Key / Postback Version однаковими
  для цих store view (задайте їх на рівні сайту), або увімкніть **Stores → Configuration → General →
  Web → Url Options → Add Store Code to Urls**, щоб `callback_url` кожного store view містив його
  код магазину.
- Значення, не задані на рівні магазину, успадковуються з рівня сайту, а рівень сайту - з default,
  як завжди: достатньо налаштувати лише те, що справді відрізняється між сайтами.
- Якщо перевірений постбек стосується замовлення з **іншого** магазину, ніж визначений за запитом
  (наприклад, через хибно налаштований базовий URL), модуль пише попередження
  `postback.store_mismatch`. Постбек усе одно застосовується, **якщо в обох магазинів однаковий
  Public Key** - це звичайний випадок, бо ключ одного акаунта NovaPay зазвичай задають один раз і
  успадковують. Якщо ж Public Key у цих магазинів **різні**, перевірений підпис належить іншому
  акаунту NovaPay, ніж той, якому довіряє магазин замовлення, тому постбек **відхиляється** і
  логується як CRITICAL (`postback.store_key_mismatch_rejected`); виправте базові URL (або
  увімкніть код магазину в URL) - і повторна доставка від NovaPay потрапить у правильний магазин.

Див. також примітку на початку [Огляду налаштувань](#огляд-налаштувань).

**Що станеться, якщо `/v1/session` чи `/v1/payment` завершаться помилкою при оформленні
замовлення?** Замовлення залишається в поточному (очікуючому) статусі, кошик відновлюється,
покупець бачить повідомлення про помилку, подія логується - нічого не списується і не скасовується.

**Де зберігаються session id / статус / RRN / код підтвердження / замаскований PAN NovaPay?**
Внутрішньо - у `sales_order_payment.additional_information` платіжного запису замовлення (той самий
стандартний механізм Magento, яким будь-який метод оплати зберігає метадані шлюзу). Для адміністратора
це відображається на перегляді замовлення, у блоці "NovaPay" - session id, статус сесії, paytype,
RRN, код підтвердження, замаскований PAN та суми повернень по позиціях.
